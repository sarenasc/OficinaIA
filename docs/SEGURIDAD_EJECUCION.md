# Seguridad de la ejecución dual

El venv no aísla privilegios. Un Job Object limita recursos y el ciclo de vida, pero tampoco reemplaza un sandbox de seguridad. El trabajador nativo ejecuta únicamente código de aplicación revisado: analiza CSV con parámetros estrictos y consulta su diagnóstico. No admite eval, exec, rutas de ejecutables, plugins, instalación de paquetes ni código generado por agentes. Tampoco se concede automáticamente una herramienta o recurso a ningún agente existente.

python.execute ahora tiene dos contratos mutuamente excluyentes. operation/parameters permite statistics.mean, sports.group, csv.read y csv.create; code/resources exige Docker. El esquema rechaza campos adicionales, nombres desconocidos y mezclas de contratos. El worker admite sólo el catálogo y sus parámetros revisados, con comprobación de valores finitos y límites propios. csv.create devuelve contenido generado al backend; los recursos y la publicación verificada siguen bajo autorización. Una aprobación no habilita código libre nativo. La versión anterior que bloqueaba todo python.execute en native queda sustituida por esta distinción explícita.

La protección principal nativa es el catálogo fijo: entrada limitada y copiada desde recurso autorizado a staging privado, proceso independiente `python -I`, entorno mínimo sin secretos, límites Windows de memoria/procesos, timeout, cancelación, salida JSON y publicación autorizada. El CSV es dato, nunca instrucciones. El worker no recibe la base de datos ni credenciales. La publicación se realiza en el backend con `publish_bytes`, verificación SHA256 y un nombre de salida nuevo.

El trabajador sigue ejecutándose bajo la cuenta del usuario. No hay filtro de red por SO, token restringido ni permisos de archivo equivalentes a los de un contenedor. No ejecutar código arbitrario nativo hasta implementar y verificar Windows Sandbox o un servicio con cuenta/token y ACL restringidos. No basta con añadir una aprobación o cambiar el agente a trusted. Alterar archivos del programa/venv por la cuenta local queda fuera de esta protección.

Docker sigue siendo obligatorio para scripts libres. Conserva los límites y permisos de Etapa 3; el host no recibe código como comando de shell. Todos los backends pasan por herramientas asignadas, capacidades y esquemas, sin rebajar el nivel requerido en auto. Los resultados completos y auditorías siguen en Execution; el modelo recibe el resumen acotado ya existente.

Los estados de jobs no incluyen código ni parámetros secretos. Los errores persistidos pasan por el redactor existente. El historial registra timestamps, motor, herramienta y estado; un reinicio marca running como interrupted sin repetir acciones. El cierre del Job Object mata los procesos asociados. Hay una ventana breve entre crear el proceso y asociarlo al Job Object: admisible para este worker fijo, no suficiente para un sandbox de código arbitrario. No se promete limitación de CPU por cuota en modo nativo; el catálogo, los datos acotados, concurrencia y tiempo de pared delimitan el trabajo. Docker sí tiene cuota CPU.

Los controles de rutas, aprobaciones SQL, Vault, SSRF y límites PDF de Etapa 3 continúan vigentes. Cancelar una tarea después de que un artefacto ya se publicó no deshace ese artefacto. SQL/HTTP mantienen sus propios timeouts; la cancelación inmediata nueva se aplica a estos procesos Python.
